What we test

The assistant and the app, as one system

An assistant is only as safe as the tools and data behind it. Most of what goes wrong is ordinary access control, reached through a chat box.

One customer's data shown to another

We plant marked test records in one account, then ask the assistant for them from a different account, in several ways.

Instructions hidden in data

One account saves a record containing an instruction aimed at the assistant. We check whether the assistant obeys it when another user asks an ordinary question.

Actions it should not take

We ask the assistant to change a test record that belongs to someone else, then look at the record to see whether it did.

The web app around it

Pages and endpoints that answer without signing in, one account opening another's records, unescaped input, leaked stack traces, and missing browser protections.

What a finding looks like

Text planted by one user made the assistant act on another user's record

This is from our sample report, run against a demo app we built with deliberate flaws. One test account shared a note containing an instruction. When the second account asked for a summary of its notes, the assistant followed the instruction and tagged one of that user's own notes.

The report gives the fix alongside: treat what the assistant reads as data, and ask the user to confirm before any tool call that changes something.

How it works

Three steps, and you approve the boundaries first

Step 1

You set the boundaries

A staging address, two made-up test accounts, and a small file on the site that proves you control it. You approve the exact hosts, paths and time window.

Step 2

We run a bounded assessment

We map the app, plant marked test data, and run a fixed set of non-destructive checks at a low request rate. You can stop it at any time.

Step 3

You get proof, fixes and a retest

Each finding shows the request that caused it, the redacted evidence, why it matters and how to fix it. After you fix, we rerun the same checks and show what closed.

How we keep it safe

Built to be run against something you care about

Strict scope

Requests go only to the hosts and paths you approved. Redirects and links to anywhere else are refused and logged.

Nothing destructive

No deleting, no password guessing, no load testing. Forms are listed, not submitted. Checks that change a test record need your approval each run.

Proof before a claim

A finding is marked confirmed only when planted test data turns up where it should not, or a marker appears after the fact.

Honest coverage

The report lists what was not tested. It never says your application is secure.

Probe is a focused check of a defined set of weaknesses, not a full penetration test. It does not replace one, and a clean result covers only what the report says was tested.
